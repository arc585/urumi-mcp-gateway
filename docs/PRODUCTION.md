# Production-like deployment on a k3s VPS

The **same Helm chart** as local; only `deploy/helm/urumi/values-prod.yaml` differs. This guide takes a fresh
Ubuntu VPS to `https://store.<domain>` and `https://app.<domain>/mcp`.

## What changes between local and production (all through Helm values)

| Concern | Local (Kind, `values-local.yaml`) | Production (k3s, `values-prod.yaml`) |
|---|---|---|
| Cluster | Kind: Kubernetes in a Docker container on the Mac | k3s: single-binary Kubernetes on the VPS |
| Ingress controller | Traefik installed by us in `traefik` | Traefik bundled with k3s in `kube-system` (`networkPolicies.ingressControllerNamespace`) |
| Hostnames / DNS | `*.urumi.test` in `/etc/hosts` | real DNS A records → VPS IP (`store.host`, `gateway.host`) |
| Ports | 8880/8843 on 127.0.0.1 (`ingress.publicPort`) | 80/443 on the public IP |
| TLS | none (HTTP) | cert-manager + Let's Encrypt (`ingress.tls.enabled`, `clusterIssuer`) |
| HTTP → HTTPS | — | Traefik Middlewares from the chart redirect port 80 to 443 and send HSTS (`templates/ingress-tls.yaml`); cert-manager's solver Pod is allowed through default-deny |
| Storage | Kind's `standard` (local-path) | k3s' `local-path` (`*.persistence.storageClass`, larger sizes) |
| Images | built locally, `kind load`, tag `dev` | GHCR, immutable version tags (`*.image.repository/tag`), optional `imagePullSecrets` |
| Secrets | generated by the chart into `urumi-store` / `urumi-gateway` | **created by you** (`store.existingSecret`, `gateway.existingSecret`); chart creates none |
| LLM key | Secret `urumi-llm` created by you | same |

What does **not** change: templates, resources and their limits, probes, NetworkPolicies, non-root containers,
application code, the tool-naming scheme, and the definition-of-done behaviour.

## 1. VPS, DNS, firewall

- VPS: 2 vCPU / 4 GB RAM minimum (4 GB is comfortable for WordPress + MariaDB + Postgres + 5 small services),
  Ubuntu 24.04, ~40 GB disk.
- DNS: `A store.<domain> → <VPS IP>` and `A app.<domain> → <VPS IP>`. Certificates need DNS first.
- Firewall: allow 22, 80, 443; allow 6443 (Kubernetes API) only from your IP, or use an SSH tunnel.

```sh
sudo ufw allow 22 && sudo ufw allow 80 && sudo ufw allow 443 && sudo ufw enable
```

## 2. Install k3s

```sh
# --secrets-encryption: Secrets are encrypted at rest in k3s' datastore (not just base64).
curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--secrets-encryption" sh -
sudo k3s kubectl get nodes                                   # Ready
sudo k3s kubectl -n kube-system get pods | grep traefik      # bundled ingress controller
sudo k3s kubectl get storageclass                            # local-path (default)
```

Use kubectl from your laptop: copy `/etc/rancher/k3s/k3s.yaml` to `~/.kube/urumi-vps.yaml`, replace
`127.0.0.1` with the VPS IP (or keep it and use `ssh -L 6443:127.0.0.1:6443 vps`), then
`export KUBECONFIG=~/.kube/urumi-vps.yaml` and `kubectl config current-context`.

## 3. Install cert-manager and the Let's Encrypt issuer

```sh
helm repo add jetstack https://charts.jetstack.io && helm repo update
helm upgrade --install cert-manager jetstack/cert-manager -n cert-manager --create-namespace \
  --set crds.enabled=true --wait
# edit the email in deploy/k3s/cluster-issuer.yaml first
kubectl apply -f deploy/k3s/cluster-issuer.yaml
kubectl get clusterissuer letsencrypt-prod      # READY True
```

## 4. Images in GHCR

Preferred: push a version tag; the CI workflow (`.github/workflows/ci.yml`) runs the tests and pushes
multi-arch (amd64 + arm64) images:

```sh
git tag v0.8.7 && git push origin v0.8.7
# → ghcr.io/<you>/urumi-gateway:0.8.7, urumi-woocommerce-mcp, urumi-demo-mcp, urumi-dashboard
```

Make the four packages public on GitHub (Packages → Package settings → Change visibility), or keep them private
and create a pull Secret (token with `read:packages`), then uncomment `imagePullSecrets` in `values-prod.yaml`:

```sh
kubectl create namespace urumi
read -s "GHCR_TOKEN?GHCR token (read:packages): " && kubectl -n urumi create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io --docker-username=<github-user> --docker-password="$GHCR_TOKEN" && unset GHCR_TOKEN
```

Manual alternative from the Mac (Apple Silicon builds arm64 by default; most VPSs are amd64):

```sh
docker buildx build --platform linux/amd64 -f services/gateway/Dockerfile -t ghcr.io/<you>/urumi-gateway:0.8.7 --push .
```

## 5. Create the Secrets (on the cluster, never in Git)

Random values are generated on the spot; nothing is typed or stored in files.

```sh
kubectl create namespace urumi   # if not created above
# Pod Security Admission: reject anything below baseline; warn on anything below restricted (only WordPress is).
kubectl label namespace urumi pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted pod-security.kubernetes.io/audit=restricted

kubectl -n urumi create secret generic urumi-store-credentials \
  --from-literal=mariadb-root-password="$(openssl rand -hex 24)" \
  --from-literal=mariadb-password="$(openssl rand -hex 24)" \
  --from-literal=wordpress-admin-password="$(openssl rand -base64 18)" \
  --from-literal=woocommerce-consumer-key="ck_$(openssl rand -hex 20)" \
  --from-literal=woocommerce-consumer-secret="cs_$(openssl rand -hex 20)"

kubectl -n urumi create secret generic urumi-gateway-credentials \
  --from-literal=api-key-pepper="$(openssl rand -hex 32)" \
  --from-literal=upstream-encryption-key="$(openssl rand -base64 32 | tr '+/' '-_')" \
  --from-literal=bootstrap-admin-key="urm_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')" \
  --from-literal=postgres-password="$(openssl rand -hex 24)" \
  --from-literal=shipping-token="$(openssl rand -hex 24)"

read -s "LLM_KEY?Paste LLM API key: " && kubectl -n urumi create secret generic urumi-llm \
  --from-literal=api-key="$LLM_KEY" && unset LLM_KEY        # zsh; in bash: read -s -p "..." LLM_KEY
```

| Secret | Keys | Used by |
|---|---|---|
| `urumi-store-credentials` | `mariadb-root-password`, `mariadb-password`, `wordpress-admin-password`, `woocommerce-consumer-key`, `woocommerce-consumer-secret` | MariaDB, WordPress, setup Job, WooCommerce MCP |
| `urumi-gateway-credentials` | `api-key-pepper`, `upstream-encryption-key` (Fernet), `bootstrap-admin-key`, `postgres-password`, `shipping-token` | gateway, Postgres, shipping MCP |
| `urumi-llm` | `api-key` | gateway (chat) |

## 6. Install

Edit `values-prod.yaml`: `store.host`, `gateway.host`, emails, and the image owner if you forked (`ghcr.io/arc585`).
The image tags must equal the chart's `appVersion`; CI enforces that, and that the git tag matches. Then:

```sh
helm template urumi deploy/helm/urumi -n urumi -f deploy/helm/urumi/values-prod.yaml | less   # review
helm upgrade --install urumi deploy/helm/urumi -n urumi -f deploy/helm/urumi/values-prod.yaml \
  --wait --wait-for-jobs --timeout 20m
```

## 7. Verify

```sh
kubectl -n urumi get pods,pvc,ingress,networkpolicy
kubectl -n urumi get certificate                       # urumi-store-tls, urumi-app-tls READY True
curl -I https://store.<domain>/shop/                   # 200, valid certificate
curl -s -o /dev/null -w '%{http_code}\n' https://app.<domain>/mcp     # 401 without a key
curl -sI http://app.<domain>/mcp | head -1                           # 308: plain HTTP is redirected to HTTPS
curl -sI https://app.<domain>/ | grep -i strict-transport            # HSTS header present
kubectl -n urumi create job --from=cronjob/urumi-backup backup-now && \
  kubectl -n urumi wait --for=condition=complete job/backup-now --timeout=15m && \
  kubectl -n urumi logs job/backup-now --all-containers | tail -5    # first backup: three files listed
kubectl -n urumi get secret urumi-gateway-credentials -o jsonpath='{.data.bootstrap-admin-key}' | base64 -d; echo

URUMI_APP=https://app.<domain> URUMI_STORE=https://store.<domain> \
URUMI_GATEWAY_SECRET=urumi-gateway-credentials URUMI_STORE_SECRET=urumi-store-credentials \
  .venv/bin/python scripts/verify_dod.py          # the full definition-of-done run, against the VPS
```

External MCP clients then use `https://app.<domain>/mcp` with a member key.

## Production limits of this single-node setup (and what to do next)

- **One node, local disks:** `local-path` volumes live on the VPS disk; losing the VPS loses data unless backed up
  (`docs/OPERATIONS.md` → backups). The backup CronJob (`backups.enabled`) keeps its dumps on the same disk; copy them off the VPS on a
  schedule (`docs/OPERATIONS.md`), or move to a block-storage CSI driver.
- **Single replicas:** WordPress, MariaDB, and Postgres run one replica each. The gateway and MCP servers are
  stateless and could scale (`replicaCount`); WordPress would need shared (RWX) storage first.
- **Secrets:** k3s `--secrets-encryption` encrypts them at rest; anyone with `get secret` RBAC in `urumi` can still
  read them, so keep cluster-admin access to yourself.
- **Mail:** no SMTP is configured; order emails are not sent.
